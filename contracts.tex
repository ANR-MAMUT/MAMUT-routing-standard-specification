\section{Current static benchmark families}\label{sec:families}
This section inventories the existing static collections and separates observed storage from the proposed defaults. The 21 October storage audit records 1,976 static descriptors. It inspected complete first matrix rows, not every entry: 684,443 entries across 1,776 inspected rows, including available sidecars and coordinate-derived rows. The separate 23 October SINTEF audit covers every entry of its 468 matrices \autocite{onyrStaticStorageAudit2026,onyrSintefAudit2026}. The author list and ORCID identifiers follow the MAMUT-routing citation file in its recorded source revision \autocite{pichonMAMUTRouting2026}.

Sintef2008 uses the hierarchical objective: minimize vehicles, then total distance. SINTEF's public convention specifies Euclidean distance, equal travel times, double-precision calculation and 2-decimal table reporting. It does not publish the complete operation sequence of its private checker \autocite{sintefSolomon2008,sintefDocumentation2008}. The new exact profile is therefore an explicitly versioned MAMUT SINTEF-derived finite-matrix model. We do not claim to have uniquely reconstructed SINTEF's hidden evaluator.

Dimacs2021 minimizes total cost subject to any declared fleet limit, without a reward for using fewer vehicles. The competition defines distances truncated to 1 decimal place in original units. MAMUT stores the corresponding factor-10 integer convention and scales temporal data consistently. Its 468-instance curation includes reduced Solomon variants in addition to the competition's 356 full-size instances. It \mustnot{} be described as merely a change of units for SINTEF, since per-arc truncation changes the model \autocite{dimacsVRPTWRules2021,onyrStaticStorageAudit2026}.

Ortec2022, Poryos2026 and Mamut2026 use the mono-cost objective in the inspected static records. A route-count lower bound or \id{k} in an instance name \mustnot{} be treated as a fleet constraint. A non-null \id{num_vehicles} is an upper bound, while null leaves the fleet unrestricted in this core. An adapter \must{} preserve the declared instance restriction and record any discrepancy with upstream data as a curation issue.

Road distances can be asymmetric and need not satisfy triangle inequality. Euclidean and road metrics can use different units. For Poryos/Mamut, fastest quantities are in seconds and shortest quantities in meters. Every manifest \must{} record the cost unit and, for VRPTW, the time unit and cost-to-travel interpretation. Scaling a VRPTW instance requires scaling windows, service times and depot bounds consistently. The static core does not support an implicit conversion between distance costs and a separate time matrix.

The 340 distinct referenced static road sidecars include 320 present in the storage audit. The 20 absent Mamut sidecars concern the documented large-POI publication policy. A descriptor with unavailable materialization is an identified but unevaluated instance, not a conforming evaluated result. Recreating those sidecars and verifying their pins is required before checking such instances. The Poryos static \id{tight} and \id{spread} variants are not TD-paired comparisons. TD-related files in these repositories do not enter the static count \autocite{pichonPoryos2026,pichonMamut2026,onyrStaticStorageAudit2026}.

\section{Generation and matrix materialization}\label{sec:generation}
This section defines what must be retained from generation and how a materialized matrix becomes an input. A benchmark revision \must{} identify its raw sources, instance bytes, sidecars, source hashes, generator revision, parameters, units, rounding rules and materialization recipe. It \must{} record random seeds and dependency versions where they affect emitted values. Imported data \may{} identify a known artifact while stating that part of its pre-publication generation is unknown. Missing provenance \mustnot{} be replaced by an invented generator description.

\subsection{Generation modes and quantization}
We distinguish imported integers, binary64 values without decimal quantization, binary64-generated values subsequently quantized on a decimal grid, and newly designed exact-decimal or rational generation. Generation arithmetic does not determine instance semantics automatically. Under the retained standard, a generated decimal token is read as binary64 even when its generator rounded to 3 decimal places.

For an exact rational $x$ and decimal precision $d\geq0$, define
\[
Q_d(x)=10^{-d}\operatorname{roundEven}(10^d x).
\]
At an exact half-integer, $\operatorname{roundEven}$ selects the even integer. Floor quantization is $10^{-d}\lfloor10^d x\rfloor$. Toward-zero quantization instead discards the fractional part of $10^d x$. Floor and toward zero agree for the nonnegative arc quantities here, but are distinct operations in general. A generation manifest \must{} identify the rule and the stage at which it acts. Loading an already published grid token \mustnot{} quantize it again.

\begin{algorithm}[htbp]
\caption{Exact decimal-grid quantization}
\begin{algorithmic}[1]
\Require Exact rational $x$, decimal precision $d\geq0$
\State $p/q\gets 10^d x$ with $q>0$
\State $(k,r)\gets\operatorname{divmod}(p,q)$, with $0\leq r<q$
\If{$2r>q$ or ($2r=q$ and $k$ is odd)}
\State $k\gets k+1$
\EndIf
\State \Return $k/10^d$
\end{algorithmic}
\end{algorithm}

The reference implements this definition as \id{quantize_decimal}. Python's \id{round(x, 3)} acts on the actual binary64 value of $x$, so its decimal result can differ from rounding a desired exact decimal input. The retained historical recipe is recorded as the actual call, rather than silently substituted with decimal-first quantization \autocite{pythonRound2026}.

\subsection{Historical recipes and proposed authority}
For integer-coordinate SINTEF generation, compute $N=(x_i-x_j)^2+(y_i-y_j)^2$ with integers and evaluate the historical \id{math.sqrt(N)} call after integer-to-binary64 conversion. DIMACS then applies binary64 multiplication by 10 and \id{int}, which truncates toward zero. The published matrices define the revision's operands. Replacing this recipe by an integer square-root construction, \id{hypot}, extended precision or exact geometry is a new recipe unless equality with all authoritative entries is established \autocite{onyrStaticStorageAudit2026,onyrSintefAudit2026}.

For Poryos/Mamut Euclidean rederivation, the current recipe parses coordinates as binary64, subtracts each coordinate in binary64, calls \id{math.hypot(dx, dy)}, and applies \id{round(value, 3)}. Road matrices are generated using the recorded routing pipeline and 3-decimal rounding before publication. Their published cost sidecars are used directly. Recomputing shortest paths from a new OpenStreetMap snapshot is regeneration of a different artifact unless the full identity checks succeed \autocite{pichonPoryos2026,pichonMamut2026,onyrStaticStorageAudit2026}.

This draft proposes binding each authoritative materialized matrix to a semantic digest in addition to raw-file hashes. For a coordinate-derived collection, the release process freezes the selected recipe, materializes its matrix and publishes its digest. A consumer \may{} reconstruct the matrix using the recipe, but \must{} obtain the published semantic digest before claiming conformance. This is a proposed resolution of the matrix-authority question, pending review of storage and regeneration arrangements. It does not claim cross-platform bitwise portability of an unspecified \id{hypot} implementation.

For binary64 matrices, the semantic digest stream is the ASCII prefix \id{MAMUT-MATRIX-v1}, newline, \id{binary64}, newline, the matrix dimension in base 10 without leading zeros, newline, followed by every matrix entry as 8 big-endian IEEE binary64 bytes in row-major order. Zero is positive zero. For a decimal alternative, replace the interpretation line with \id{decimal} and encode each reduced $p/q$ as ASCII \id{p/q} followed by newline. Both digests use SHA-256. These streams identify the interpreted matrix, not the remaining instance constraints.

Compressed sidecars \must{} identify whether a hash covers compressed file bytes or decompressed content. We propose storing both with explicit names. A digest mismatch, unavailable sidecar or unsupported materializer \must{} stop authoritative evaluation. There is no fallback from missing road costs to Euclidean geometry. A cache key \must{} include instance identity, interpretation, materialization identity and profile, rather than instance name alone.

\subsection{An optional new exact-coordinate recipe}
For a newly designed decimal-geometric family, one can quantize Euclidean distances without approximate square roots. From exact rational coordinates compute $N=p/q\geq0$. For scale $S=10^d$, obtain $k=\lfloor\sqrt{pS^2/q}\rfloor$ by integer square root. Compare $4pS^2$ with $q(2k+1)^2$ to decide whether $S\sqrt{N}$ is below, above or at the midpoint. At equality select the even integer. Return that integer divided by $S$. The reference function \id{euclidean_decimal} implements this recipe. It is an available design option, not the historical Poryos/Mamut materializer or a new default.

\section{Instance semantics and the static core}\label{sec:core}
This section specifies the mathematical objects consumed after successful materialization. We use vertices $\{0,1,\ldots,n\}$, with depot 0. Customers have nonnegative integer demands $q_i$ and vehicles have nonnegative integer capacity $Q$. We require $q_0=0$. Fleet limit $K$ is a nonnegative integer or absent. The $(n+1)\times(n+1)$ arc matrix $c$ is finite and nonnegative, with zero diagonal. For VRPTW, $c_{ij}$ is also travel time, each vertex has a service-start window $[e_i,l_i]$ with $0\leq e_i\leq l_i$, and service duration $s_i\geq0$.

All numerical arc and temporal quantities use the retained binary64 reading: for each original token $t$, the mathematical operand is the exact rational value of $\RoundBinary(\operatorname{decimal}(t))$. Integer resource quantities are kept as integers and \must{} also be exactly representable in binary64 for this shared core, so their integer representation agrees with the retained reading. Indices, counts and identifiers are structural integers and do not undergo numerical rounding. An extension supporting larger resource integers must identify that enlarged domain explicitly.

The alternative \id{decimal-exact} interpretation maps the original JSON token directly to its exact decimal rational value. A decimal-grid profile additionally requires all arc and temporal operands to be multiples of $10^{-d}$. The test is exact divisibility after decimal parsing. Converting a token to float and then applying \id{str}, \id{repr}, or multiplication by 1000 does not implement original-token decimal interpretation. Arbitrary rational input would need a separate value encoding, such as numerator and denominator strings. This draft reserves that extension rather than guessing rational values from rounded decimals.

\begin{algorithm}[htbp]
\caption{Interpret an arc or temporal JSON token under a selected profile}
\begin{algorithmic}[1]
\Require Original valid JSON numerical token $t$, profile $P$
\If{$P$ declares binary64 interpretation}
\State $f\gets\RoundBinary(\operatorname{decimal}(t))$ using correctly rounded parsing
\State Reject nonfinite $f$, normalize signed zero
\State $x\gets$ the exact rational value of $f$
\Else
\State $x\gets\operatorname{decimal}(t)$ as an exact rational
\EndIf
\State Check integral or decimal-grid eligibility when required by $P$
\If{$P$ prescribes rounded binary64 evaluation}
\State \Return binary64 $f$
\Else
\State \Return exact rational $x$
\EndIf
\end{algorithmic}
\end{algorithm}

Published coordinates are provenance or materialization inputs according to the manifest. Once an embedded or pinned materialized matrix is authoritative, a checker \mustnot{} replace it from coordinates. The current core excludes split deliveries, multiple depots, heterogeneous vehicles, pickup loads, separate travel-time matrices and independent maximum route durations. Such features require named extensions that define their constraints and arithmetic. Unsupported features \must{} produce an explicit unsupported outcome.
