\section{Generation provenance and instance materialization}\label{sec:generation}
This section distinguishes historical generation from the materialization needed to read a published instance. Generation code and its reproducibility documentation describe how the published files were produced. Each instance is accompanied by a consumption manifest identifying its files and sidecars, default reading/evaluation profile, objective, units and supported features. The instance format and consumption manifest do not require a duplicated generation recipe or a \id{generation} object. A consumer of published arc values need not execute the code that originally produced them.

Generation documentation \must{} point to the relevant code at an immutable revision and identify the exact Python version and functions used where applicable, including the operations around \id{sqrt}, \id{hypot} and quantization. It records parameters, seeds and dependencies needed to reproduce generation when known. Imported data \may{} identify a known artifact while stating that part of its pre-publication generation is unknown. Missing provenance \mustnot{} be replaced by an invented generator description. These historical details remain separate from the manifest's normative instructions for reading the published instance.

\paragraph{Locating a benchmark instance.}
Each family repository is mounted under \path{benchmarks/<Family>/}. Its \path{mamut-collection.json} marker identifies the family and layout version. In layout 2 the path below this root begins with the problem type, followed by an optional subset and the size directory. Poryos2026 and Mamut2026 use layout 1. In either layout, a relative sidecar path in the descriptor is resolved from the collection root. For example, the Rifki-30 descriptor in \path{TDVRP/n=30/} refers to \path{sidecars/n=30/Rifki-30.atf.json.gz} from the Rifki2020 root. For a loose instance with no enclosing collection marker, the base is the descriptor's directory. The \href{https://github.com/ANR-MAMUT/MAMUT-routing-lib/blob/e032f2b9b9d1ba16a561325a07ab59cf39f8e5d5/src/mamut_routing_lib/sidecars.py}{collection resolver} implements both rules.

The \href{https://github.com/ANR-MAMUT/MAMUT-routing-archive-2026-11}{benchmark archive} preserves the earlier tree and its submodule pins. Moving a sidecar can change the path recorded in a descriptor and hence the descriptor's byte hash, even when the sidecar bytes are identical. To replay an archived evaluation, resolve the recorded path and verify the hashes at the cited revision.

\subsection{Generation modes and quantization}
We distinguish imported integers, binary64 values without decimal quantization, binary64-generated values subsequently quantized on a decimal grid, and newly designed exact-decimal or rational generation. Generation arithmetic does not determine instance semantics automatically. Under the default profile, a generated decimal token is read as binary64 even when its generator rounded to 3 decimal places.

For $x\in\Q$ and decimal precision $d\in\mathbb{N}_0$, define
\begin{equation}\label{eq:decimal-quantization}
Q_d(x)=10^{-d}\operatorname{roundEven}(10^d x)\in\Grid{d},\qquad \Grid{d}=10^{-d}\mathbb{Z}.
\end{equation}
At an exact half-integer, $\operatorname{roundEven}$ selects the even integer. Floor quantization is $10^{-d}\lfloor10^d x\rfloor$. Toward-zero quantization instead discards the fractional part of $10^d x$. Floor and toward zero agree for the nonnegative arc quantities here, but are distinct operations in general. Generation code and its documentation \must{} identify the rule and the stage at which it acts. Loading an already published grid token \mustnot{} quantize it again.

\begin{algorithm}[htbp]
\caption{Exact decimal-grid quantization}\label{alg:quantize}
\begin{algorithmic}[1]
\Require $x\in\Q$, decimal precision $d\in\mathbb{N}_0$
\State Choose $(p,q)\in\mathbb{Z}\times\mathbb{Z}_{>0}$ with $p/q=10^d x$
\State $(\ell,\rho)\gets\operatorname{divmod}(p,q)$, where $p=\ell q+\rho$ and $0\leq\rho<q$
\If{$2\rho>q$ or ($2\rho=q$ and $\ell$ is odd)}
\State $\ell\gets\ell+1$
\EndIf
\State \Return $\ell/10^d\in\Grid{d}$
\end{algorithmic}
\end{algorithm}

The reference implements this definition as \id{quantize_decimal}. Python's \id{round(x, 3)} acts on the actual binary64 value of $x$, so its decimal result can differ from rounding a desired exact decimal input. The retained historical recipe is recorded as the actual call, rather than silently substituted with decimal-first quantization \autocite{pythonRound2026}.

\subsection{Matrix authority and on-demand regeneration}\label{sec:materialization}
An instance can use embedded matrices, matrix sidecars and on-demand regeneration from published raw data. The authoritative object is the interpreted logical matrix, whether or not a dense matrix file is stored. The manifest identifies the representation through \id{materialization.kind}, using \id{embedded-matrix}, \id{sidecar-matrix} or \id{regenerated}, and binds its interpreted values to \id{materialization.matrix_sha256}. An embedded or sidecar matrix is consumed directly under the declared reading profile. Historical generation details remain in code and documentation.

If reading an instance requires regenerating arc values, including for large instances evaluated on demand, the regeneration function is part of the instance contract. The manifest \must{} pin its fully qualified callable, immutable implementation revision and content identity, numerical parameters, and an immutable environment identity covering dependencies that affect its outputs. All required raw inputs \must{} be identified by content hash. The accompanying implementation documentation gives the exact Python version, called functions and operation sequence. A mutable function name or documentation URL alone is insufficient to pin the implementation. Reusing code that also generated a dataset does not remove these loading obligations.

The \id{materialization} object records the value \id{interpretation} and its expected \id{matrix_sha256}. For \id{regenerated} values, it additionally records \id{function}, \id{implementation}, \id{parameters}, \id{environment} and \id{inputs}. The implementation identifies the versioned code artifact and its hash. The environment identifies an immutable environment record rather than duplicating its full package inventory in every instance manifest. The inputs identify the raw files and their hashes. The parameters include precision, rounding and any other choice consumed by the pinned callable. A different interpretation requires its own matching semantic digest.

The raw instance hash checks the published descriptor or input bytes. The manifest hash additionally binds the declared constraints, profile and regeneration pins. The semantic matrix digest checks that materialization reproduces the expected arc values. These checks serve different purposes: matching raw bytes alone does not verify the regenerated outputs. A reproducibility check \must{} compare the complete canonical matrix stream against the published digest. This stream can be produced incrementally from regenerated rows or entries, without allocating or distributing a dense matrix. Verifying only the arcs of one submitted solution does not establish full matrix identity.

Once established, materialization verification \may{} be reused for unchanged raw-input hashes, implementation and environment identities, parameters, interpretation and expected matrix digest. A changed dependency invalidates that reuse. No full-matrix regeneration is required for every solution evaluation. A checker can request arc values on demand or cache them, provided that these values follow the same pinned contract and its verified identity. Thus large instances do not require a stored dense matrix, while reproduction remains checkable independently of the solver's visited arcs.

For binary64 matrices, the semantic digest stream is the ASCII prefix \id{MAMUT-MATRIX-v1}, newline, \id{binary64}, newline, the matrix dimension in base 10 without leading zeros, newline, followed by every matrix entry as 8 big-endian IEEE binary64 bytes in row-major order. Zero is positive zero. For a decimal alternative, replace the interpretation line with \id{decimal} and encode each reduced $p/q$ as ASCII \id{p/q} followed by newline. Both digests use SHA-256. These streams identify the interpreted matrix, not the remaining instance constraints.

Compressed sidecars \must{} identify whether a hash covers compressed file bytes or decompressed content. We propose storing both with explicit names. A digest mismatch, unavailable sidecar or unsupported materializer \must{} stop authoritative evaluation. There is no fallback from missing road costs to Euclidean geometry. A cache key \must{} include instance identity, interpretation, materialization identity and profile, rather than instance name alone.

\subsection{An optional new exact-coordinate recipe}
For a newly designed decimal-geometric family, one can quantize Euclidean distances without approximate square roots. From coordinates in $\Q^2$, compute the squared distance $N=p/q\in\Q_{\geq0}$, with $p\in\mathbb{N}_0$ and $q\in\mathbb{Z}_{>0}$. For $d\in\mathbb{N}_0$ and scale $S=10^d\in\mathbb{Z}_{>0}$, obtain $\ell=\lfloor\sqrt{pS^2/q}\rfloor\in\mathbb{N}_0$ by integer square root. Compare $4pS^2$ with $q(2\ell+1)^2$ to decide whether $S\sqrt{N}$ is below, above or at the midpoint. At equality select the even integer. Return that integer divided by $S$, an element of $\Grid{d}$. The reference function \id{euclidean_decimal} implements this recipe. It is an available design option, not the historical Poryos/Mamut materializer or a new default.

\section{Instance semantics and the static core}\label{sec:core}
This section specifies the mathematical objects consumed after successful materialization. Let $\mathcal{C}=\{1,\ldots,n\}$ be the customer set, with $n=|\mathcal{C}|\in\mathbb{N}_0$, and $\mathcal{V}=\mathcal{C}\cup\{0\}$ the vertex set. Vertex 0 is the depot and $|\mathcal{V}|=n+1$. Customer demands and vehicle capacity satisfy $q_i,Q\in\mathbb{N}_0\cap\Fbin$, with $q_0=0$. We use $\bot$ to denote an absent value, encoded as JSON null. The fleet limit satisfies $K\in\mathbb{N}_0\cup\{\bot\}$: an integer gives the upper bound, while $K=\bot$ imposes no fleet limit.

Let $P\in\mathcal{P}$ be the selected profile from the registry in Section~\ref{sec:profiles}, and let $\mathbb{A}_P\subseteq\Q_{\geq0}$ be its admissible arc and temporal value set. Nonnegativity is part of every profile's instance contract:
\begin{equation}\label{eq:profile-domains}
\mathbb{A}_P=\begin{cases}
\Fbin\cap\mathbb{N}_0, & P=\text{\id{integer-exact-v1}},\\
\Grid{3}\cap\Q_{\geq0}, & P=\text{\id{decimal-grid-3-v1}},\\
\DecimalSet\cap\Q_{\geq0}, & P=\text{\id{decimal-exact-v1}},\\
\FbinNonneg, & \text{all other registered profiles}.
\end{cases}
\end{equation}
The matrix satisfies $c\in\mathbb{A}_P^{(n+1)\times(n+1)}$, so $c_{ij}\geq0$ for every arc $\langle i,j\rangle\in\mathcal{V}\times\mathcal{V}$, and $c_{ii}=0$ for every $i\in\mathcal{V}$. An instance containing any negative interpreted arc value is invalid under every profile. A checker \must{} reject it, without clamping the value to zero or applying a feasibility tolerance. Zero-cost arcs are permitted. For VRPTW, $c_{ij}$ is also travel time, each vertex $i\in\mathcal{V}$ has a time window $[e_i,l_i]$ with $e_i,l_i\in\mathbb{A}_P$ and $e_i\leq l_i$, and customer $i\in\mathcal{C}$ has service duration $s_i\in\mathbb{A}_P$. Only customers receive service. In every static and TD profile the depot has $s_0=0$. When an instance supplies a vertex-indexed service array, a checker \must{} reject a nonzero interpreted depot entry during instance validation. The depot window governs departure and return.

All numerical arc and temporal quantities in the retained standard use binary64 reading: for each original token $t\in\JsonNum$, first compute $f=\RoundBinary(\Dec(t))$ and require $f\in\Fbin$. An exact profile then uses $x=\RatBin(f)\in\Q$ as its arithmetic representation of that same value. Integer resource quantities are kept as integers and \must{} also be exactly representable in binary64 for this shared core, so their integer representation agrees with the retained reading. Indices, counts and identifiers are structural integers and do not undergo numerical rounding. An extension supporting larger resource integers must identify that enlarged domain explicitly.

The alternative \id{decimal-exact} interpretation maps the original JSON token directly to $x=\Dec(t)\in\DecimalSet\subseteq\Q$. A decimal-grid profile additionally requires each arc and temporal operand to belong to $\Grid{d}$ for its declared $d\in\mathbb{N}_0$. The test is exact divisibility after decimal parsing: $x\in\Grid{d}$ if and only if $10^d x\in\mathbb{Z}$. Converting a token to float and then applying \id{str}, \id{repr}, or multiplication by 1000 does not implement original-token decimal interpretation. Arbitrary rational input would need a separate value encoding, such as numerator and denominator strings. This encoding is outside the supported input profiles.

\begin{algorithm}[htbp]
\caption{Interpret an arc or temporal JSON token under a selected profile}\label{alg:interpret-token}
\begin{algorithmic}[1]
\Require Numerical token $t\in\JsonNum$, registered profile $P\in\mathcal{P}$
\If{$P$ declares binary64 interpretation}
\State $f\gets\RoundBinary(\Dec(t))\in\FbinExt$
\State Reject if $f\notin\Fbin$, normalize its signed-zero encoding
\State $x\gets\RatBin(f)\in\Dyadic\subseteq\Q$ \Comment{same numerical value as $f$}
\Else
\State $x\gets\Dec(t)\in\DecimalSet\subseteq\Q$
\EndIf
\State Reject if $x\notin\mathbb{A}_P$ \Comment{nonnegativity and profile restrictions}
\If{$P$ prescribes rounded binary64 evaluation}
\State \Return $f\in\Fbin$ for rounded arithmetic
\Else
\State \Return $x\in\Q$ for exact arithmetic
\EndIf
\end{algorithmic}
\end{algorithm}

The assignment $x\gets\RatBin(f)$ in Algorithm~\ref{alg:interpret-token} expresses an already rounded binary64 value as an exact rational. It introduces no further rounding and does not recover $\Dec(t)$ when the initial binary64 reading changed that value. Membership in $\mathbb{A}_P$ checks nonnegativity together with any integrality or grid restriction. Appendix~\ref{app:notation} works through the token \id{0.1}. Implementations may avoid constructing a rational object on a rounded-return path when equivalent domain checks can be made directly on $f$. Exact-return paths must preserve the value specified here, whether represented by a rational pair, a scaled integer or another equivalent exact structure.

Published coordinates are provenance or materialization inputs according to the manifest. Once an embedded or pinned materialized matrix is authoritative, a checker \mustnot{} replace it from coordinates. The current core excludes split deliveries, multiple depots, heterogeneous vehicles, pickup loads, separate travel-time matrices and independent maximum route durations. Such features require named extensions that define their constraints and arithmetic. Unsupported features \must{} produce an explicit unsupported outcome.
