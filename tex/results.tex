\section{Authoritative results, BKS and website values}\label{sec:results}
This section defines what a result records and what the ecosystem compares. A BKS is an accepted incumbent for one benchmark revision, objective and numerical profile. It is not an optimality certificate by itself. Each BKS retains a top-level \id{cost} field for existing clients and website display. The authoritative numerical value is stored in metadata together with its contract identity. Ranking \mustnot{} use the compatibility \id{cost} field or a 2-decimal website string.

\subsection{Exact encoding and display}
For an authoritative value $C\in\Q$, this draft selects a single canonical exact encoding: write $C=p/q$ with $p\in\mathbb{Z}$, $q\in\mathbb{Z}_{>0}$ and $\gcd(|p|,q)=1$, and store $p$ and $q$ in \id{numerator} and \id{denominator} strings. Each string contains a base-10 integer without leading plus or leading zeros. Zero has numerator string \id{"0"} and denominator string \id{"1"}. A nonzero negative numerator is allowed for general bound metadata. Feasible routing costs remain in $\Q_{\geq0}$. The reader \must{} reject noncanonical fractions, rather than silently assigning another exact byte identity to the same canonical value.

Numerator/denominator storage works for dyadic, decimal-grid and arbitrary rational results. Exact terminating decimal strings and scaled integers are possible derived views, but this version does not store multiple competing authoritative encodings. Strings avoid forcing arbitrary-size integers through clients that interpret every JSON number as binary64. Conversion to a finite-precision Decimal context is not required to read or compare the authoritative value \autocite{brayJSON2017,pythonFractions2026}.

For an exact profile with $C\in\Q_{\geq0}$, compute $\widehat C=\RoundBinary(C)\in\FbinExt$ once from the authoritative exact total with ties to even. When $\widehat C\in\Fbin$, the top-level \id{cost} is this finite round-trip JSON number, with positive zero. For a rounded profile, it is the final binary64 objective $T\in\Fbin$ already defined by that profile, whose authoritative rational encoding is $\RatBin(T)$. If $\widehat C\notin\Fbin$, this draft requires \id{cost:null} with an explicit \id{display_overflow} flag, while retaining the exact metadata. Current family adoption should verify that this exception is unnecessary for their accepted results. Whether existing clients can support nullable display values remains a release issue.

A website that shows $d\in\mathbb{N}_0$ decimal places \must{} derive its display from $Q_d(C)\in\Grid{d}$ with nearest-even ties, rather than decimal-rounding the already rounded \id{cost}. This avoids \href{https://en.wikipedia.org/wiki/Rounding#Double_rounding}{double rounding} changing the displayed decimal. The reference \id{display_decimal} implements the rule. Imported historical table values remain separate source claims, with their original precision and rounding convention recorded when known. This website rule does not assert SINTEF's undocumented tie-breaking behavior.

\subsection{Required provenance envelope}
The proposed envelope lives at \id{metadata.standard}. Its field names are a draft integration proposal and are not asserted to be accepted by current library schemas. A conforming new result \must{} include the following fields, in addition to its routes and compatibility \id{cost}:

\begin{longtable}{@{}p{4.2cm}p{11.4cm}@{}}
\toprule
Field & Meaning and required value\\
\midrule
\endhead
\id{specification} & Immutable specification revision. The earlier static fixture uses \id{mamut-static/0.1-draft}.\\
\id{benchmark_revision} & Immutable family revision identifier selected by its manifest. A library version alone is insufficient.\\
\id{manifest_sha256} & SHA-256 of the complete UTF-8 manifest bytes. The manifest does not contain its own hash.\\
\id{profile} & Full selected integrated profile identifier. Unknown identifiers are unsupported, without fallback.\\
\id{objective} & One of \id{MonoCost}, \id{HierarchicalVehicleCost} (static), \id{Duration} or \id{FleetCostDuration} (TD).\\
\id{num_routes} & Exact nonnegative structural integer, checked against the routes.\\
\id{authoritative_cost} & Reduced numerator/denominator object containing the profile's authoritative objective value.\\
\id{routes_sha256} & SHA-256 of the canonical route stream for exact/canonical profiles, or submitted-order route stream for submitted-flat.\\
\id{evaluation} & Checker name, source revision or source-file hash, runtime/environment identity, and verification status. This describes the actual evaluator invocation.\\

\bottomrule
\end{longtable}

An optional sibling object \id{metadata.optimality} records an optimality claim or rigorous gap as specified in Section~\ref{sec:proof}. It is separate from \id{metadata.standard.evaluation}, which records incumbent verification. Omit \id{optimality} when no claim is recorded. Its absence means neither a proof of nonoptimality nor a zero optimality gap. A boolean \id{optimal} or \id{proven} is not a substitute for this structured object.

The accompanying instance manifest \must{} record the family and revision, problem type, declared objective, \id{default_profile}, cost/time units, exact instance file SHA-256, all required sidecar or raw-input identities, materialization contract, identity of the materialized matrix or ATFs, and the allowed feature set. Static matrix regeneration follows Section~\ref{sec:materialization}. TD manifests identify the materialized ATFs and their verification procedure under Section~\ref{sec:td-core}. Historical generation code and reproducibility documentation remain separate and need not be duplicated in the manifest. The manifest's raw hash binds its constraints and choices to the result. A published family manifest \may{} reference per-instance manifests by hash. An instance name is informative within that identity chain, never the sole input identity. The result's \id{profile} records the profile actually used. A separately identified alternative evaluation \mustnot{} silently replace the manifest's default authority for BKS ranking.

The route-digest stream is ASCII \id{MAMUT-ROUTES-v1}, newline, the number of routes $|\mathcal{S}|$, newline, then one line per route: the length $|\mathbf{r}_{\mathcal{C}}|$ of its stored customer subsequence, a colon, its customer indices separated by commas, and newline. Integers use base 10 without leading zeros. Depot endpoints are implicit in this serialized stream. Route order follows the submitted enumeration $\mathbf{s}$ for submitted-flat and $\operatorname{canon}(\mathcal{S})$ otherwise. Empty customer subsequences have already been rejected. Raw submitted files \should{} also be preserved by byte hash when they serve as external provenance.

The static companion\textquotesingle{}s generated \id{example-result.json} and \id{example-manifest.json} provide a complete synthetic example with real hashes, rather than placeholders that resemble verified production identities. The normalized example instance is also provided. The example result's evaluation identifies it as a synthetic fixture. It omits \id{metadata.optimality}, since no solver run or optimality claim is recorded.

\begin{algorithm}[htbp]
\caption{Serialize a valid authoritative result}\label{alg:serialize-result}
\begin{algorithmic}[1]
\Require Valid solution $\mathcal{S}$ with enumeration $\mathbf{s}$, cost $C\in\Q_{\geq0}$, manifest, profile $P$
\State Reduce $C=p/q$, with $(p,q)\in\mathbb{N}_0\times\mathbb{Z}_{>0}$ and $\gcd(p,q)=1$
\State Encode $p$ and $q$ as canonical decimal integer strings
\State $\widehat C\gets\RoundBinary(C)\in\FbinExt$ once, with ties to even
\State Set compatibility \id{cost} to $\widehat C$ if $\widehat C\in\Fbin$, otherwise null
\State Attach manifest hash, profile, objective, route count and route-stream hash
\State Attach evaluator identity and incumbent verification status
\State Preserve any separate \id{metadata.optimality} claim with its original target and evidence
\State \Return result envelope, preserving source provenance separately
\end{algorithmic}
\end{algorithm}

\subsection{Checking supplied values and comparing incumbents}
A supplied authoritative cost is an assertion. A checker or result validator \must{} recompute feasibility and cost under the declared authority and compare the exact value, route count, profile and bound input identities. A mismatch rejects the result envelope. The routes can still be investigated separately as a candidate, but the inconsistent record is not a verified result. The compatibility \id{cost} \must{} agree with its specified rounded projection. Historical costs \may{} be retained in a separate source-provenance record instead of being overwritten.

Candidates and incumbents \must{} have the same benchmark revision, interpreted inputs, objective and authority before an improvement comparison. For exact profiles compare reduced rational costs directly, with the vehicle-count tier where applicable. On equality of the full key, the store \must{} retain the incumbent already stored when the candidate is evaluated. Discovery dates and reported departures do not enter this comparison. Distinct exact values can round to the same binary64 \id{cost} and the same website display. Such a collision \mustnot{} turn a strict improvement into a tie. For rounded profiles compare their authoritative final rounded values under the declared operation sequence.

Website gaps and experiment reference scores \must{} identify the reference revision and use the authoritative values. For a mono-cost minimization reference $R\in\Q_{>0}$ and candidate cost $C\in\Q_{\geq0}$, the signed reference deviation $100(C-R)/R\in\Q$ can be computed exactly before display rounding. This is a deviation from a stated reference, not automatically a certified optimality gap. For hierarchical objectives, a distance-only comparison is meaningful within a fixed vehicle-count tier. A different tier \must{} be shown as a different hierarchical outcome, without hiding it in a scalar percentage. Zero denominators require an explicit undefined state or a separately defined metric.

\section{Solver arithmetic and proof assurance}\label{sec:proof}
This section separates a checked incumbent from an optimality guarantee. The target profile defines the problem independently of search arithmetic. Binary64 or compensated search \may{} still target the exact-binary problem. To establish optimality, however, a proof must bound that same target problem. Merely recording tolerances or applying accurate final summation does not make unsafe search decisions valid.

In our 26 October 2026 inventory of all 1,976 curated static CVRP/VRPTW instance descriptors and their 1,976 BKS records, we find no stored full routing-optimality claims, certificates or \id{optimal} flags to migrate. Mamut2026 separately records bin-packing fleet lower bounds, marked proven for 270 of its 330 metric variants. These concern the minimum number of bins for the demands, not the optimal \id{MonoCost} routing objective. The absence of a stored routing claim does not imply that an instance has no optimum known elsewhere. The structured claim object below defines how future claims can be recorded without requiring a historical static-claim migration.

The optional \id{metadata.optimality} object has a \id{status} of \id{solver-reported-optimal}, \id{rigorous-gap} or \id{numerically-certified-optimal}. It records a \id{target}, \id{solver}, \id{evidence}, \id{lower_bound} and \id{proof}. The target identifies the specification, benchmark revision, manifest hash, objective and profile of the claimed problem. The solver record identifies its name, version or source revision, arithmetic contract and numerical tolerances. Evidence identifies the source of the claim, its date and the available logs or artifacts. Unknown details and unavailable bounds or proofs are explicit null values. A missing historical profile \mustnot{} be inferred from the profile used for a new incumbent evaluation.

For \id{solver-reported-optimal}, \id{proof} can be null: the status preserves what an identified solver reported, without asserting independent certification. A rigorous status additionally requires justified bound or proof evidence, its applicable numerical contract, verifier identity and verification outcome. Recording a solver name, a zero reported gap or a text field named \id{certificate} is insufficient by itself. The target profile and the solver's search arithmetic are separate facts, even when both use binary64. A solver can search approximately while targeting an exact profile, but its bound must justify that target before a rigorous status is assigned.

For minimization, exact incumbent verification gives a feasible upper bound $U\in\Q_{\geq0}$. Let $z^{\circledast}$ denote the scalar optimum of the target problem. A rigorous lower bound $L\in\mathbb{R}$ for that same objective gives $L\leq z^{\circledast}\leq U$. A numerical Branch-and-Price-and-Cut (BPC) run needs safe pricing, dominance, cuts, branching, pruning and bound treatment to justify the left inequality. A final route checker establishes only the right inequality. Rounding column costs or suppressing a feasible pricing label can invalidate a bound even when the returned routes pass final checking.

One can combine approximate search with exact or conservatively bounded proof-critical computations. As an illustration, for a basic set-partitioning model with target fleet size $\kappa\in\mathbb{N}_0$, restrict solutions to $|\mathcal{S}|=\kappa$. Let $\pi_i\in\mathbb{R}$ be a dual value for each $i\in\mathcal{C}$, and suppose a valid global pricing bound establishes
\[
c_{\mathbf{r}}-\sum_{i\in\mathbf{r}_{\mathcal{C}}}\pi_i\geq-\eta\quad\text{for every feasible route }\mathbf{r},\qquad\eta\geq0.
\]
Then $L=\sum_{i\in\mathcal{C}}\pi_i-\kappa\eta$ is a valid lower bound for that fixed-fleet model. Checking only the route returned by an approximate pricer does not establish the premise. A full BPC formulation must include its cuts and branching terms. Numerically exact BPC for bin packing provides a related example of safe dual bounds and fixed-point pricing, rather than evidence that a routing implementation is automatically certified \autocite{baldacciNumericallyExact2024}. SCIP likewise documents a mixed approach to exact solving with explicit requirements on participating components \autocite{scipExact2026}.

If every fixed-fleet objective belongs to a known lattice of spacing $\delta\in\Q_{>0}$, a rigorous $L>U-\delta$ proves optimality: any better feasible value would be at most $U-\delta$. A conventional tolerance such as $10^{-6}$ does not automatically close a much finer binary lattice. For a hierarchical objective, a proof must also establish the minimal vehicle-count tier before closing the distance gap at that tier. A certified positive gap is a valid outcome when strict closure is unavailable.

The evaluation and optimality records \must{} distinguish incumbent verification, source-reported claim, and any verified bound or proof. Absent proof evidence \mustnot{} be represented as certified optimality. Search, checking, certification and end-to-end runtimes \should{} be recorded separately with timer scopes. Reporting these scopes is essential when comparing methods that provide different assurance. Implementing a proof-producing BPC engine or running a safe-pricing pilot is a separate research task, not a prerequisite for adopting this static evaluation standard.

An archived proof for a rounded-cost or other interpretation remains attached to that model. Reevaluating its incumbent under the new exact profile can establish a new feasible upper bound, but does not transfer its lower bound or optimality claim. Publication provenance and the original claim remain preserved without silently upgrading their numerical assurance.
