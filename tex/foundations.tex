\section{Purpose, scope and status}\label{sec:scope}
We consider single-depot routing problems with homogeneous vehicle capacity and mandatory single visits. The static Capacitated Vehicle Routing Problem (CVRP) and Vehicle Routing Problem with Time Windows (VRPTW) use a fixed arc-cost matrix. In Time-Dependent (TD) routing, the departure time on an arc determines its arrival time. We retain each benchmark revision\textquotesingle{}s declared objective and units.

The words \must{}, \mustnot{}, \should{} and \may{} express requirements, recommendations and permitted choices within this draft. An implementation claiming a profile \must{} return its specified feasibility verdict and authoritative objective for supported inputs. A resource limit \must{} produce an explicit failure or inconclusive outcome, never a fabricated feasible result. Passing a finite fixture suite is evidence of conformance rather than a proof for every input.

We distinguish three questions. \emph{Operational conformance} asks whether an evaluator implements the prescribed recipe. \emph{Mathematical fidelity} asks whether that recipe computes the intended mathematical model over declared values. \emph{Reproducibility} asks whether recorded artifacts and an environment reproduce the result. Sequential \href{https://en.wikipedia.org/wiki/Floating-point_arithmetic}{floating-point arithmetic} can satisfy its operational contract while differing from exact summation. An exact rational evaluator can faithfully evaluate rounded matrix entries without reconstructing unrounded geometry. A result reproduced on one host does not establish cross-platform conformance.

\section{Binary64 values, arithmetic and JSON}\label{sec:binary64}
This section introduces the numerical distinctions needed by the contracts. We use $\mathbb{N}_0=\{0,1,2,\ldots\}$ for nonnegative integers, $\mathbb{Z}$ for integers, $\Q$ for rational numbers and $\mathbb{R}$ for real numbers. A subscript such as $\Q_{\geq0}$ restricts a set to its nonnegative elements. Appendix~\ref{app:notation} consolidates the numerical domains, conversion operators and routing symbols in a notation table.

We read numerical operands using IEEE 754 binary64, the 64-bit double-precision format. A normal finite value has 53 significant binary digits. Appendix~\ref{app:notation} gives the encoding for normal and subnormal values \autocite{oracleIEEEArithmetic}.

The \href{https://en.wikipedia.org/wiki/Unit_in_the_last_place}{unit in the last place (ulp)} describes the spacing between adjacent representable values near a given value. This spacing is not uniform across the full range of binary64 values.

We denote the set of finite binary64 numerical values by $\Fbin$. Its elements are the values of the finite normal and subnormal encodings, with both signed-zero encodings identified with the numerical value 0. In particular, $\Fbin\subsetneq\Q$: every $f\in\Fbin$ has an exact rational value, although not every rational number is representable in binary64. We write $\RatBin:\Fbin\hookrightarrow\Q$ for the inclusion that expresses $f$ as an exact rational. This map preserves the numerical value and introduces no rounding. In the pseudocode, $f\in\Fbin$ denotes a binary64 operand, while $x=\RatBin(f)\in\Q$ denotes the same value represented for exact arithmetic.

We write $\RoundBinary:\mathbb{R}\to\FbinExt$, where $\FbinExt=\Fbin\cup\{-\infty,+\infty\}$, for binary64 rounding using \href{https://en.wikipedia.org/wiki/Rounding#Rounding_half_to_even}{rounding to nearest with ties to even}: an exact midpoint is rounded to the value whose significand has even least significant bit. Input conversion and prescribed binary64 evaluator operations require finite results. Overflow when projecting an exact objective affects only its display, as specified in Section~\ref{sec:results}. We require gradual underflow and normalize signed zero. For $a,b\in\Fbin$, prescribed binary64 addition is
\begin{equation}\label{eq:binary64-addition}
a\oplus_{64}b=\RoundBinary\bigl(\RatBin(a)+\RatBin(b)\bigr)\in\FbinExt.
\end{equation}
The addition inside $\RoundBinary$ is exact rational addition, followed by 1 rounding. We use $+$ for exact addition and $\oplus_{64}$ when the result is rounded to binary64. Rounding after every addition generally differs from rounding only the exact final sum. Binary64 addition is \href{https://en.wikipedia.org/wiki/Associative_property#Nonassociativity_of_floating-point_calculation}{not associative}, so regrouping operands can change the result. A compiler or processor that reassociates additions, retains wider unrounded intermediates, flushes subnormals or contracts an expression into a different operation sequence does not implement that prescribed recipe.

Every finite binary64 number is a \href{https://en.wikipedia.org/wiki/Dyadic_rational}{dyadic rational}, that is, an element of $\Dyadic=\{m2^{-b}:m\in\mathbb{Z},\ b\in\mathbb{N}_0\}$. Hence $\Fbin\subsetneq\Dyadic\subsetneq\Q$, and we can sum binary64 values exactly and compare exact arrival times without requiring a particular programming language. Such exact sums need not belong to $\Fbin$. For example, the binary64 value loaded from \id{0.1} is $3602879701896397/36028797018963968$, whereas the exact decimal value is $1/10$. In Python, \id{Fraction(float("0.1"))} and \id{Fraction("0.1")} construct these different values. Neither operation recovers any physical value that preceded rounding \autocite{pythonFloatingPoint2026,pythonFractions2026}.

The \href{https://en.wikipedia.org/wiki/JSON}{JavaScript Object Notation (JSON)} format specifies numeric text, without assigning every consumer a binary64 mathematical interpretation. Its interoperability guidance discusses the commonly exact integer range $[-(2^{53}-1),2^{53}-1]$ \autocite{brayJSON2017}. We therefore declare semantics by field role and profile. Structural integers such as customer indices and route counts remain integers. Numerical quantities such as matrix weights and service times are interpreted according to the selected instance contract, even when a JSON token has no decimal point.

Let $\JsonNum$ be the set of valid JSON numerical tokens, and let $\Dec:\JsonNum\to\DecimalSet\subseteq\Q$ map a token to the exact decimal rational spelled by its characters. Here $\DecimalSet=\{m10^{-d}:m\in\mathbb{Z},\ d\in\mathbb{N}_0\}$ is the set of finite-decimal rationals. For a token $t\in\JsonNum$, binary64 interpretation first computes $f=\RoundBinary(\Dec(t))$ and requires $f\in\Fbin$. Exact-binary evaluation then uses $x=\RatBin(f)\in\Q$, while exact-decimal interpretation uses $x=\Dec(t)\in\Q$ directly. The intermediate binary64 rounding is the difference between these paths.

Shortest round-trip \href{https://en.wikipedia.org/wiki/Serialization}{serialization} can represent a binary64 value with far fewer decimal digits than its exact decimal expansion. Under correctly rounded reading, the serialized token reloads to the same finite value. Different spellings can denote that same value, so a textual change can alter a file hash while preserving its interpreted numerical data. Conversely, interpreting the shortest spelling as an exact decimal rational changes its meaning. A loader \mustnot{} infer a decimal contract from the number of printed fractional digits \autocite{pythonFloatingPoint2026}.

The standard loader \must{} retain numeric tokens until their roles and profile are known. It \must{} reject duplicate JSON members, non-JSON numerical extensions such as NaN and Infinity, nonfinite binary64 conversions, and booleans used as numbers. Finite subnormal values are allowed. Values rounded to zero by binary64 conversion have zero numerical meaning under that interpretation. Signed zero is normalized to positive zero for semantic digests and result serialization. Raw artifact bytes retain their original identity. The reference uses token-preserving hooks provided by Python's JSON decoder \autocite{pythonJSON2026}.

\section{Four separate contracts}\label{sec:layers}
This section separates the decisions that together define a benchmark. A \emph{generation contract} records source data, transformations, numerical operations, quantization, random seeds, software and emitted artifacts through generation code and its reproducibility documentation. An \emph{instance contract} assigns mathematical values and problem structure to the published artifacts through an accompanying manifest, including the default reading/evaluation profile and any materialization needed to obtain arc values. An \emph{evaluation contract} maps an interpreted instance and submitted routes to a verdict and objective. A \emph{result contract} specifies serialization, comparison, provenance, Best-Known Solution (BKS) storage and the strength of any proof claim.

\begin{tabularx}{\linewidth}{@{}lXX@{}}
\toprule
Stage & Question & Example obligation\\
\midrule
Generation & How were the published values obtained? & Document the generating code, environment and rounding.\\
Instance & What do the values mean after loading or rederivation? & Declare the profile and pin any regeneration function.\\
Evaluation & What arithmetic and constraints are authoritative? & Check feasibility and compute the declared objective on the materialized values.\\
Result & What value is ranked and what does a claim establish? & Store a reduced fraction and bind it to the profile.\\
\bottomrule
\end{tabularx}
\end{center}

For this standard, the retained instance interpretation is binary64 after generation or rederivation. This applies to the 3-decimal Poryos/Mamut values as well as full-precision SINTEF-derived matrices. Exact decimal and scaled-grid alternatives are presented explicitly, but they \mustnot{} silently replace the retained binary64 reading. Exact evaluation then means exact arithmetic on those interpreted binary64 values. It does not mean exact decimal arithmetic on their printed spellings.

These choices remain independent of a solver's internal arithmetic. A solver \may{} search with binary64, compensated sums, integers, intervals or rational numbers. Its accepted final incumbent \must{} be checked under the benchmark revision's selected contract. Its lower-bound and optimality claims have the separate obligations in Section~\ref{sec:proof}.
