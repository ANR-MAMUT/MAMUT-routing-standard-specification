\section{Purpose, scope and conformance}\label{sec:scope}

MAMUT-routing publishes benchmark instances alongside the routes of their reported best-known solutions \autocite{pichonMAMUTRouting2026}. A researcher who compares a new route with the published one needs to know what a number in the instance means, which constraints the route satisfies and which objective the benchmark ranks. A benchmark revision fixes those choices, and the program that applies them to a submitted route is called the \emph{checker}. We consider the single-depot Capacitated Vehicle Routing Problem (CVRP) and the Vehicle Routing Problem with Time Windows (VRPTW), together with their Time-Dependent (TD) counterparts. In all of them, vehicles share a common capacity and every customer must be visited exactly once. Each revision declares its objective and units. Whereas a static benchmark assigns a fixed cost to each directed arc, a TD benchmark assigns it an Arrival Time Function (ATF), so that the duration of a route can depend on the time at which it leaves the depot.

This document is the standard that MAMUT-routing implements. It is explanatory first and meant to be read by humans, so it states the conventions at a high level, gives the reasons behind them and works through examples, while it leaves implementation-level details such as file layouts, field names and parameters to the open-source code of MAMUT-routing. By design, the text therefore does not suffice on its own to reimplement a checker. It nevertheless takes precedence over the code. A contradiction between the two should never happen, and if one is found, the code is in error and is corrected to follow this document.

The checker needs the same numerical arc data that define the benchmark, and a family can supply them in several ways. It can embed a cost matrix in its instance file, or keep the arc data in an accompanying file called a sidecar, which for TD routing can hold the knots defining the ATFs.\footnote{\textcite[Sec.~3.1]{visserEfficientMoveEvaluations2020} and \textcite[Sec.~2]{blauthVehicleRoutingTimedependent2024} use \emph{breakpoint} for the points defining a continuous piecewise-linear function. We use \emph{knot} for each stored pair of departure and arrival times because the sidecar also preserves collinear points and identical consecutive pairs, and can store distinct arrival times at the same departure time to encode a jump. We deliberately retain every knot so that independent implementations can reproduce and verify the same ordered sequence of binary64 operands.} It can also supply compact inputs together with a pinned procedure that reconstructs those values. For example, a road graph can yield a static matrix of shortest-path distances, and a road graph with a traffic overlay can yield a collection of TD arc functions. In either case, a verified reconstruction stands in for the stored JSON. To make this verification possible, the publisher pins the input files and code to specific versions and records a SHA-256 digest of the complete interpreted matrix or set of knots. This digest acts as a fingerprint of the agreed sequence of numerical values. An independent implementation can then regenerate the values, compare the digest and check routes against the verified data. Section~\ref{sec:materialization} explains what must be pinned and when this verification can be reused.

The profiles \id{binary64-exact-v1} and \id{td-binary64-exact-v1} fix the same boundary between materialization and evaluation. Each numerical arc or time operand has the value obtained by reading it in IEEE~754 binary64, and the checker uses that value exactly in all subsequent arithmetic. The static profile sums the costs of the traversed arcs, while the TD profile evaluates the published arc functions and finds, for each route, the earliest depot departure attaining the minimum feasible duration. We distinguish a \emph{profile}, which specifies the answer, from a \emph{backend}, which is an implementation of that profile, for example a Python evaluator using rational numbers or a native evaluator using integers where the arithmetic permits. A result identifies both.

The words \must{}, \mustnot{}, \should{} and \may{} express requirements, prohibitions, recommendations and permitted choices within a profile. An implementation claiming a profile \must{} give its specified feasibility verdict and authoritative objective for supported inputs. If it cannot finish, for example because a fixed-width integer would overflow, it \must{} report failure or an inconclusive outcome. Note that a finite fixture suite gives evidence about the cases it exercises, but conformance over the full input domain also depends on the algorithm and its implementation.

Three questions arise when two checkers disagree, or when both reproduce a value that surprises the reader.
\begin{description}
\item[Operational conformance.] Did the checker perform the operations required by the declared profile? A sequential \href{https://en.wikipedia.org/wiki/Floating-point_arithmetic}{floating-point sum} can conform to a released checker's recipe even when rounding after each addition gives a different answer from summing the same operands exactly.
\item[Mathematical fidelity.] Which mathematical problem do those operations solve? Summing published road distances exactly gives the exact length of the route in that matrix, yet this sum still inherits the rounding of each distance if the generator applied one. Likewise, exact TD interpolation evaluates the published knots, whose resolution was fixed when the arc function was generated.
\item[Reproducibility.] Can another team obtain the same inputs and repeat the evaluation? Its regenerated arc values can be checked against the published digest before either team evaluates a route. Once the inputs match, the teams can investigate any remaining discrepancy in scheduling, aggregation or display.
\end{description}

\section{From JSON numbers to exact operands}\label{sec:binary64}

The \href{https://en.wikipedia.org/wiki/JSON}{JavaScript Object Notation (JSON)} format represents numbers as text. For instance, \id{0.1} is a numerical token, i.e. a sequence of characters accepted by the JSON number grammar, whereas the quoted value \id{"0.1"} is a JSON string. A numeric instance field requires the former, although a result format may explicitly require strings for the digits of a large numerator or denominator. A JSON decoder also distinguishes the numerical token \id{1} from the Boolean literal \id{true}. Beyond these syntactic distinctions, the grammar alone leaves the numerical interpretation of a token to its consumer. JSON interoperability guidance identifies $[-(2^{53}-1),2^{53}-1]$ as the range within which binary64 consumers can agree on all integer values \autocite{brayJSON2017}.

The \emph{role of the field} therefore matters. Structural integers, including vertex indices and route counts, are read as integers, whereas arc costs, time-window bounds, service durations and ATF knot coordinates are numerical operands. Their binary64 reading also applies to tokens written without a decimal point. Let $\JsonNum$ be the set of valid JSON numerical tokens and $\Dec(t)$ the exact decimal rational spelled by token $t\in\JsonNum$. The token \id{0.1} spells $1/10$, as do \id{0.10} and \id{1e-1}. We write $\Q$ for the rational numbers, $\mathbb{Z}$ for the integers and $\mathbb{N}_0$ for the nonnegative integers. Appendix~\ref{app:notation} collects the numerical domains, conversion operators and routing symbols.

\paragraph{Reading a binary64 value.}
IEEE~754 \href{https://en.wikipedia.org/wiki/Double-precision_floating-point_format}{binary64} is the 64-bit double-precision floating-point format, in which a normal finite value has 53 significant binary digits. The spacing between successive representable values changes with their magnitude, and the \href{https://en.wikipedia.org/wiki/Unit_in_the_last_place}{unit in the last place (ulp)} describes this local precision. At input we round the exact decimal value to the nearest binary64 value, with a tie going to the representation whose significand has an even least significant bit. We denote this \href{https://en.wikipedia.org/wiki/Rounding#Rounding_half_to_even}{nearest-even rounding} by $\RoundBinary$. We require gradual underflow, including finite subnormal values, and a token whose nearest binary64 value is zero contributes zero. We normalize signed zero to positive zero for numerical comparison, semantic digests and result serialization, while the raw file retains the originally written bytes \autocite{oracleIEEEArithmetic}.

Let $\Fbin$ be the set of finite binary64 numerical values and $\FbinExt=\Fbin\cup\{-\infty,+\infty\}$. Every $f\in\Fbin$ is a \href{https://en.wikipedia.org/wiki/Dyadic_rational}{dyadic rational}, i.e. a number of the form $m2^{-b}$ with $m\in\mathbb{Z}$ and $b\in\mathbb{N}_0$, and we write $\RatBin:\Fbin\hookrightarrow\Q$ for the inclusion that expresses $f$ as a rational while preserving its value. Reading a numerical token for either exact profile thus takes two steps, the first of which performs the rounding.
\begin{equation}\label{eq:binary64-reading}
f=\RoundBinary(\Dec(t))\in\Fbin,\qquad x=\RatBin(f)\in\Q.
\end{equation}
For \id{0.1}, the resulting rational is $3602879701896397/36028797018963968$. In Python, \id{Fraction.from_float(float("0.1"))} returns this value, whereas the call \id{Fraction("0.1")} asks Python to parse the decimal characters directly and therefore returns $1/10$. Both fractions are exact for their respective arguments \autocite{pythonFloatingPoint2026,pythonFractions2026}.

\begin{algorithm}[htbp]
\caption{Read an arc or temporal operand for either exact profile}\label{alg:interpret-token}
\begin{algorithmic}[1]
\Require An unquoted JSON numerical token $t\in\JsonNum$
\State $f\gets\RoundBinary(\Dec(t))$
\State Reject if $f\notin\Fbin$. Normalize its signed-zero encoding.
\State $x\gets\RatBin(f)$
\State Check the numerical domain required by the field.
\State \Return $x$
\end{algorithmic}
\end{algorithm}

A loader \must{} distinguish a token's role before a conversion can lose information. It \must{} reject duplicate JSON object members, a Boolean or string in a numerical operand field, the non-JSON tokens \id{NaN} and \id{Infinity}, and numerical tokens whose binary64 conversion overflows. A parser can use the original token text or an equivalent correctly rounded conversion, while structural integer fields retain their integer syntax and domain. For instance, the Python reference uses token-preserving hooks in the JSON decoder \autocite{pythonJSON2026}.

\paragraph{Printed decimals and decimal grids.}
A shortest round-trip \href{https://en.wikipedia.org/wiki/Serialization}{serialization} writes enough decimal digits for a correctly rounded reader to recover the same binary64 value, whereas the exact decimal expansion of that value would often take many more digits. Different spellings can therefore change a file's byte hash while preserving every interpreted operand. A printed number with 3 fractional digits can also come from a generator that quantizes distances to the grid $\Grid{3}=10^{-3}\mathbb{Z}$, on which the exact decimal token \id{215.359} denotes $215359/1000$. Since its reduced denominator contains a factor of 5, the nearest binary64 value differs from the grid value, and the binary64 profiles use that rounded value even when every published token was generated to 3 decimal places. Multiplying such a binary64 operand by 1000 and converting it to an integer can therefore change the instance that a solver evaluates.

\paragraph{Rounding during an evaluation.}
For two binary64 operands $a,b\in\Fbin$, a rounded addition means
\begin{equation}\label{eq:binary64-addition}
a\oplus_{64} b=\RoundBinary\bigl(\RatBin(a)+\RatBin(b)\bigr)\in\FbinExt .
\end{equation}
The addition within $\RoundBinary$ is exact, while repeating $\oplus_{64}$ rounds after each operation. For example, if $a=2^{53}$, then $(a\oplus_{64}1)\oplus_{64}1=a$, whereas $a\oplus_{64}(1\oplus_{64}1)=a+2$. This \href{https://en.wikipedia.org/wiki/Associative_property#Nonassociativity_of_floating-point_calculation}{failure of associativity} explains why the summation order matters for a released profile that specifies rounded additions, since reassociation or wider unrounded intermediates can change such a recipe. In the exact profiles, by contrast, ordinary $+$ denotes rational addition and the exact sum in this example is $a+2$. An exact static sum can, however, exceed the binary64 range, and TD interpolation can introduce denominators with factors other than 2, so Section~\ref{sec:results} specifies how to store and display the resulting rational objectives.

\section{Four contracts for a benchmark result}\label{sec:layers}

A result must identify both the problem that was solved and the meaning of its reported value. The following four contracts separate the decisions involved.

\begin{center}
\begin{tabularx}{\linewidth}{@{}lXX@{}}
\toprule
Contract & Question & Example obligation\\
\midrule
Generation & How did the benchmark authors obtain the published data? & Identify the source graph, routing metric and rounding used to produce the distances.\\
Instance & Which problem and numerical values does this revision define? & Declare units, constraints and the default profile. Pin the materialization of the matrix or ATFs.\\
Evaluation & What does a submitted route achieve on those values? & Check all visits, capacities and windows. For TD duration, select the earliest minimizing departure.\\
Result & What is ranked, and what does the claim establish? & Store the reduced rational objective with the profile and the backend used for certification.\\
\bottomrule
\end{tabularx}
\end{center}

For example, a static family may publish road distances rounded to 3 decimal places. The generation contract then explains where the distances and their rounding came from, the instance contract fixes the binary64 values a reader obtains, and the evaluation contract sums the traversed arc values exactly. Finally, the result contract records that sum and ties it to the verified instance and route set. A different solver may search with binary64, scaled integers, interval bounds or rational arithmetic, yet each submitted incumbent is checked under the same contract for its benchmark revision. A proof of optimality additionally requires a bound for that objective on that feasible set.
