\section{Prescribed binary64 alternatives for static evaluation}\label{sec:rounded}
For each rounded profile, parse every arc and temporal quantity as finite binary64, normalize zero and apply the shared structural checks. Initialize each objective accumulator to positive binary64 zero. Round each addition immediately to nearest binary64 with ties to even. Reject overflow.

\begin{algorithm}[htbp]
\caption{Binary64 objective modes after route validation}\label{alg:rounded-objective}
\begin{algorithmic}[1]
\Require Validated route set $\mathcal{S}$, enumeration $\mathbf{s}$, $c_{ij}\in\FbinNonneg$, rounded profile
\State $\mathbf{s}_P\gets\mathbf{s}$ for submitted-flat, otherwise $\operatorname{canon}(\mathcal{S})$
\State $T\gets+0_{64}$ \Comment{$T\in\Fbin$}
\For{each route $\mathbf{r}$ in the sequence $\mathbf{s}_P$}
\State $U\gets+0_{64}$ \Comment{$U\in\Fbin$}
\For{each arc $\langle i,j\rangle$ in $\operatorname{arcs}(\mathbf{r})$}
\If{grouped mode} \State $U\gets U\oplus_{64}c_{ij}$
\Else \State $T\gets T\oplus_{64}c_{ij}$ \EndIf
\EndFor
\If{grouped mode} \State $T\gets T\oplus_{64}U$ \EndIf
\EndFor
\State \Return $\RatBin(T)\in\Q_{\geq0}$ \Comment{same numerical value as final $T$}
\end{algorithmic}
\end{algorithm}

For rounded temporal feasibility, use the same service-start notation, with $t_0=e_0\in\FbinNonneg$. After predecessor $i$, compute $t_j=\max(e_j,(t_i\oplus_{64}s_i)\oplus_{64}c_{ij})$ and check $t_j\leq l_j$. The parentheses require the departure addition to round before the travel addition. Upon return from the last customer $i$, compute $t_0^{\mathrm{ret}}=\max(e_0,(t_i\oplus_{64}s_i)\oplus_{64}c_{i0})$ and check $t_0^{\mathrm{ret}}\leq l_0$. Here $s_0=0$ in the first-leg recurrence. Every addition result and accepted service-start time must remain in $\FbinNonneg$, and any overflow is rejected. Each route has an independent clock. Objective grouping does not change this clock recurrence. Maximum and comparisons select and compare the current binary64 values without an added epsilon.

The grouped mode \must{} use explicit binary64 additions both inside and across routes. An implementation \mustnot{} replace them with a version-dependent language \id{sum}, parallel reduction, \id{fsum}, extended accumulator or reassociated expression. For submitted order, the original enumeration $\mathbf{s}$ is part of the evaluated solution identity and \must{} be retained alongside the mathematical route set $\mathcal{S}$. Its authoritative value can depend on both $\mathcal{S}$ and $\mathbf{s}$. Canonicalizing that file and then evaluating it as submitted order can change its authoritative value.

The result fraction records the exact value of the final binary64 accumulator. Each result \must{} retain its profile identifier to identify the arithmetic used for timing and cost.
