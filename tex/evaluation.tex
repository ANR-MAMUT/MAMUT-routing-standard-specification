\section{Feasibility and cost of a submitted solution}\label{sec:exact}\label{sec:profiles}

A submission specifies which customers each vehicle visits and in what order. From these sequences we must decide whether the vehicles can serve all customers and, if so, what the declared objective is worth. The two questions already differ on a route with constant travel times. A vehicle can wait for a customer to open without changing the travel cost of its tour, although that wait does increase the time the vehicle spends away from the depot. We distinguish these quantities throughout, since static benchmarks charge for the arcs traversed, whereas time-dependent benchmarks charge for the elapsed duration of the route.

Both profiles start from the instance identified in Section~\ref{sec:materialization}, and under \id{binary64-exact-v1} (static) and \id{td-binary64-exact-v1} (TD) each finite binary64 operand $f$ contributes its exact rational value $\RatBin(f)$. In particular, a service start exactly at its deadline satisfies that constraint, whereas any strictly later start violates it, however small the excess. The same interpretation applies to arc values, the horizon, window endpoints, service durations and any fixed vehicle charge. Appendix~\ref{app:notation} collects the notation.

\subsection{Which customers does each vehicle serve?}

Let $\mathcal C=\{1,\ldots,n\}$ be the customer set and let vertex $0$ be the depot. A route is a vector $\mathbf r=\langle v_1=0,v_2,\ldots,v_{m-1},v_m=0\rangle$ of length $m\geq3$, whose JSON array contains just the nonempty customer subsequence $\mathbf r_{\mathcal C}=\langle v_2,\ldots,v_{m-1}\rangle$. For example, the array \id{[2,1]} prescribes the three directed arcs $(0,2)$, $(2,1)$ and $(1,0)$. Since these arcs are directed, reversing the array can change both cost and feasibility.

Before checking visits, we validate the instance. The static matrix has one row and column per vertex, including the depot, with $c_{ij}\geq0$ and $c_{ii}=0$. Customer demands $q_i$ and vehicle capacity $Q$ are nonnegative integers exactly representable in binary64, and the depot demand is $q_0=0$. Each supplied service duration satisfies $s_i\geq0$, and each window satisfies $0\leq e_i\leq l_i$. The checker must reject a nonzero depot service duration, even on a route whose customers have no windows. In the TD model all arcs share the finite departure horizon $0\leq h_0<h_1$, although windows and the route itself may restrict the feasible departures to a single instant within that horizon.

We first read the submitted enumeration $\mathbf s$ with all entries present, in which every entry in a customer subsequence must be an index in $\mathcal C$ and every customer must occur exactly once. Checking this on the enumeration before forming a set detects, for example, a file that submits the same route twice. For every route we then require $\sum_{j=2}^{m-1}q_{v_j}\leq Q$, and empty customer sequences are invalid. If a fleet limit $K$ is supplied, the number of routes must be at most $K$. Note that with $n=0$ the empty solution is admissible and its cost is zero.

Once these checks succeed, $\mathcal S$ denotes the set of routes and $|\mathcal S|$ is the realized fleet size. For storage we sort the routes lexicographically by their customer subsequences, which gives $\operatorname{canon}(\mathcal S)$ without changing any visit order within a route. The exact departure and duration of each TD route accompany that route in this stored order (Section~\ref{sec:results}).

\subsection{From depot departure to depot return}

Consider a vehicle that leaves vertex $i$ at time $d_i$. In the static problem with time windows, the matrix entry $c_{ij}$ is both the cost and the travel time of the directed arc $(i,j)$. In the TD problem, the ATF $\alpha_{ij}$ instead gives the arrival clock time at $j$ for a departure at $i$. The common forward calculation at a customer $j$ is
\begin{align*}
 u_j &= \begin{cases} d_i+c_{ij} & \text{static},\\ \alpha_{ij}(d_i) & \text{TD},\end{cases} & \text{(arrival)}\\
 t_j &= \begin{cases} \max(u_j,e_j) & \text{with window }[e_j,l_j],\\ u_j & \text{without a window},\end{cases} & \text{(service start)}\\
 d_j &= t_j+s_j. & \text{(departure)}
\end{align*}

The window constrains the start of service, so we require $t_j\leq l_j$ whenever the window is present, while service may finish after $l_j$. On the last arc we use the same arrival rule with destination $0$ and check the depot return deadline $l_0$ when specified. The elapsed duration ends when the vehicle reaches the depot. For static capacitated routing without time windows, by contrast, the coverage, capacity and fleet checks suffice for feasibility.

In the static problem with time windows we can start at depot opening, $d_0=e_0$, because later departures can only delay arrival on a constant-time arc. At a customer, both waiting until opening and adding service preserve that order, so induction along the route shows that this schedule gives the earliest attainable service start at each customer and the earliest return to the depot. Hence, if it misses a deadline, every schedule for the same order misses that deadline. Note that starting the clock at the declared opening matters when $e_0>0$.

For example, suppose both legs of a one-customer route take $2$ time units, the customer accepts service starts in $[7,9]$, service takes $2$, and the depot window is $[0,15]$. A vehicle leaving at $0$ arrives at $2$, waits until $7$, finishes service at $9$ and returns at $11$, so the route is feasible. Its static travel cost is $2+2=4$, yet the vehicle has spent $11$ time units away from the depot. We now keep the same customer sequence and allow the departure time to vary.
